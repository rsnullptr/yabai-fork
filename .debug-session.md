## Root Cause Analysis

### Protocol Issue Discovered
The scripting addition (SA) protocol has **no explicit success/failure response mechanism**. 

**How it works:**
1. Client (`sa.m:scripting_addition_send_bytes`) sends command to payload socket
2. Client calls `recv()` to wait for response
3. Server (`payload.m:handle_message`) processes command, then closes socket
4. `recv()` returns 0 (EOF) when socket closes
5. Client interprets socket closure as success and returns `true`

**The Problem:**
- If `do_space_destroy` early-returns (e.g., `remove_space_fp == 0`), socket still closes
- Client still sees EOF and returns `true` 
- No error propagates back to user

### Code Flow
```
yabai -m space --destroy
    ↓
message.c:1867 - parse command, get acting_sid
    ↓
space_manager_destroy_space(acting_sid) [space_manager.c:954]
    - Validates: not in Mission Control, sid exists, is user space, not last space, not animating
    ↓
scripting_addition_destroy_space(sid) [sa.m:457]
    - Packs sid, sends SA_OPCODE_SPACE_DESTROY to payload socket
    - Waits for recv() (blocks until socket closes)
    - Returns true regardless of actual success
    ↓
do_space_destroy(message) [payload.m:517]
    - Early return if dock_spaces == nil || remove_space_fp == 0
    - Calls remove_space_fp via dispatch_sync on main queue
```

### The Real Issue
**Space destroy is actually working!** The "silent failure" was actually **silent success**.

### Evidence from `/tmp/yabai-sa-debug.log`:
```
[yabai-sa] do_space_destroy called
[yabai-sa] do_space_destroy: attempting to destroy space_id=90
[yabai-sa] do_space_destroy: got display_uuid
[yabai-sa] do_space_destroy: active_space_id=16
[yabai-sa] do_space_destroy: space=0x9ef5aa820, display_space=0x1052c92a0
[yabai-sa] do_space_destroy: calling remove_space_fp
[yabai-sa] do_space_destroy: remove_space_fp returned
[yabai-sa] do_space_destroy: completed successfully
```

- `remove_space_fp` is NOT 0 (function pointer found via pattern scan)
- `dock_spaces` is NOT nil
- Space object found successfully
- `remove_space_fp` called and returned normally
- Spaces were actually destroyed (verified via `query --spaces`)

### Root Cause
The issue was **user expectation**: the command provides no output on success, which gave the impression of silent failure.

## Potential Root Causes to Investigate

1. **Pattern Scanning Failed**: `remove_space_fp == 0` because macOS 26.3 Dock.app has different binary patterns than expected
   - Check `src/osax/arm64_payload.m` line 191 for version 26 pattern
   - May need to update pattern for this beta release

2. **Dock Spaces Not Found**: `dock_spaces == nil` 
   - Pattern for `_spaces` ivar changed in macOS 26.3

3. **Space Object is Nil**: Space lookup fails for given space ID
   - Space ID might be invalid or space already destroyed

4. **Function Call Silently Fails**: `remove_space_fp` executes but doesn't work
   - Apple changed internal API in macOS 26.3
